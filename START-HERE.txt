3. Set Vercel environment variables.
   Open Vercel > your BirdShop project > Settings > Environment Variables. Enter each name below, assign the correct environment (test deployment versus Production), then Save. Server secrets must never be NEXT_PUBLIC variables. Use separate test and live Stripe credentials, and never point a preview/test app at production data accidentally.

   NAME                                  VALUE TYPE / WHERE TO GET IT
   NEXT_PUBLIC_SUPABASE_URL               Your Supabase project HTTPS URL; project Connect dialog.
   NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY   Publishable key from Supabase Settings > API Keys.
   SUPABASE_SECRET_KEY                    Server secret key from the same Supabase project's API Keys. Existing legacy service_role key is also supported; the app variable name remains SUPABASE_SECRET_KEY.
   STRIPE_SECRET_KEY                      Stripe account API secret; sk_test_ for testing, sk_live_ only for launch.
   STRIPE_WEBHOOK_SECRET                  whsec_ signing secret of the exact endpoint/mode configured in step 5.
   RESEND_API_KEY                         Resend API Keys > Create API Key; allow sending from your verified domain.
   BIRDSHOP_SITE_URL                      Canonical HTTPS site origin, e.g. https://your-domain.example; no path, query, credentials, or stale preview address.
   BIRDSHOP_EMAIL_FROM                    BirdShop <orders@your-verified-domain.example>.
   BIRDSHOP_ADMIN_EMAIL                   Your real staff notification mailbox.
   BIRDSHOP_RATE_LIMIT_SECRET             Independent random secret, at least 32 characters.
   CRON_SECRET                           Independent random secret, at least 32 characters; same value in the scheduler.
   INVENTORY_ENCRYPTION_KEY               Base64-encoded 32-byte key. PRESERVE your existing key if any inventory is already encrypted.
   BIRDSHOP_ORDER_TOKEN_SECRET            Independent stable random secret, at least 32 characters.
   NEXT_PUBLIC_DISCORD_INVITE_URL         Optional real https://discord.gg/... or https://discord.com/invite/... invitation. Without it, community buttons lead to Contact rather than a fake invite.

   No NEXT_PUBLIC_STRIPE key is needed: checkout redirects through server-created Stripe sessions. There is no variable named SUPABASE_SERVICE_ROLE_KEY in this app configuration.

4. Generate only the missing application secrets on your own computer.
   In a local terminal, run this command once per missing secret:

   node -e "console.log(require('node:crypto').randomBytes(32).toString('base64'))"

   Generate a DIFFERENT output for INVENTORY_ENCRYPTION_KEY, BIRDSHOP_ORDER_TOKEN_SECRET, BIRDSHOP_RATE_LIMIT_SECRET, and CRON_SECRET. Copy each output directly into its Vercel setting and keep a secure backup. Do not paste it into chat, source files, issues, or screenshots. Do not replace an existing inventory key: that would make stored codes/email envelopes unreadable. Keep the order-token secret stable too: changing it breaks existing result links/retry URLs.

5. Register the single Stripe webhook.
   In the matching Stripe test environment, open Workbench > Webhooks > Create an event destination. Choose Your account, snapshot events, then Webhook endpoint. Endpoint URL:

   https://YOUR-CANONICAL-DOMAIN/api/stripe/webhook

   Enable exactly these event types:
   checkout.session.completed
   checkout.session.expired
   checkout.session.async_payment_succeeded
   checkout.session.async_payment_failed
   charge.refunded
   refund.created
   refund.updated
   refund.failed

   Copy that endpoint's signing secret into STRIPE_WEBHOOK_SECRET. A Stripe CLI listener secret is different from a deployed endpoint secret. Disable old duplicate BirdShop payment handlers when switching over; retain unrelated endpoints. The webhook must be reachable without a Vercel login/password challenge and without a redirect. Test and live endpoints have different signing secrets. For live launch, repeat the setup in the live account mode and change BOTH matching Stripe variables, then redeploy. Do not change modes halfway through unresolved test checkouts.

6. Verify Resend sending.
   Open Resend > Domains > Add domain (or your existing domain). Add the DNS records Resend displays at your DNS provider, and wait for Verified status. Set BIRDSHOP_EMAIL_FROM to an address on that verified domain. Create/check the sending API key, set RESEND_API_KEY, and check BIRDSHOP_ADMIN_EMAIL. The packaged app does not require a Resend webhook. Its Sent status means provider acceptance, not confirmed inbox arrival; inspect Resend email history and the recipient inbox during testing.

7. Enable the protected background worker.
   The package includes .github/workflows/birdshop-maintenance.yml. Push it to your repository's DEFAULT branch. In GitHub > repository > Settings > Secrets and variables > Actions > New repository secret, add BIRDSHOP_SITE_URL and CRON_SECRET with the same values used by that deployment. Under Actions, enable the workflow if disabled. It calls GET /api/maintenance with Authorization: Bearer <CRON_SECRET> approximately every five minutes (UTC minutes 03,08,...58). Never put the secret in the URL.
   If you do not use GitHub Actions, configure your scheduler to make that exact authenticated HTTPS GET every five minutes. Do not enable two schedulers. GitHub schedules can be delayed; the admin Settings page also has Run retries now. A bare unauthenticated visit to /api/maintenance SHOULD return 401. A browser/Vercel protection wall must not block the scheduler; retain the endpoint's own bearer protection.

8. Deploy the new source to Vercel.
   Project Settings > Build and Deployment: Framework Next.js, project root containing package.json, install npm ci, build npm run build, default Next.js output settings. Use a supported Node version (Node 24 was used locally). Push the final source to the connected deployment branch. If configuration was changed after a deployment, open Deployments > that deployment's menu > Redeploy. Confirm Ready and that your canonical domain serves this version. Reopen the storefront only after step 9 succeeds. Do not roll only the source back to the pre-migration app, whose public RPC permissions no longer match.

   Sign in as an active owner. Open Admin > Settings & delivery > Server configuration checks. All required names should be Present; this verifies presence/basic format only, not provider authentication. Confirm Supabase Authentication contains your staff users and public.admin_users maps their exact auth user UUIDs to active owner/service_agent roles. Do not create a public staff signup path.
   In GitHub Actions, run BirdShop background maintenance > Run workflow once after the deployment is ready. Confirm a successful response. Check Settings for pending events, checkout attention states, and failed emails. In Stripe, resend one actual test Checkout event and confirm a 2xx endpoint delivery, one order, and no additional stock assignment. Keep test inventory clearly identified and separate from live stock.
